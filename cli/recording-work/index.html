Recording work

Talks about: artifacts, cli, corrections, and facts

You record evidence. Stages follow.

Create a ticket

tik new support-request --title "login fails on Firefox"

The ticket pins the process definition’s content hash at creation, so it is judged by the rules it was minted under until somebody deliberately moves it with tik reprocess.

Created beneath a store, a ticket inherits its context as signed facts: repo=<name> from the enclosing git repository, plus any .tik-facts.edn maps on the way down, nearest winning, with anything explicit beating both.

Assert facts

tik set 3184 severity=:high resolution.ref=abc123def456

Dotted keys nest, so parked.reason="waiting on legal" writes the path [:parked :reason]. Values parse as EDN, and a bare word becomes a keyword — severity=high and severity=:high mean the same thing, which keeps facts out of the swamp of free-form strings.

Links are facts too:

tik set 3184 link.depends-on=9c21f0a4

tik next then holds 3184 back while 9c21 is unsettled, and tik status names the blocker.

Attach evidence

tik attach 3184 ./crash-repro.sh
tik comment 3184 reproduced on a clean profile, video attached

Artifacts are stored by hash. A comment is an artifact too — a text blob attached by its digest — which is why comments need no event type of their own.

Correct the record

Nothing is edited or deleted. Corrections are new events:

tik set 3184 severity=:critical              # supersedes; history retained
tik retract 3184 resolution.ref --reason "wrong commit"
tik dispute 3184 category --reason "this is billing"
tik dispute 3184 category --withdraw         # take back your own objection

A later assertion supersedes an earlier one. A retraction says the claim should not exist and offers no replacement. A dispute rejects the value its author saw when they raised it, so only a different value answers it. In every case the stage regresses by derivation — there is no rollback step.

Signed claims and attestations

tik attest 3184 {:ci :green}

An attestation is a signed claim whose meaning the kernel does not interpret. Lenses read it, and the :attested-within guard checks that a fresh-enough one exists — a replayed “CI green” from last month is cryptographically valid and fails that guard honestly.

Review in one batch

tik review review.verdict=approved --list
tik review review.verdict=approved

A reviewer’s queue is mostly signatures over work somebody else already recorded: a merge commit an agent asserted, a definition nobody has published yet. tik review lists everything that waits on you alone and signs it after one confirmation, or without asking when you pass --yes.

A ticket is offered when every reason its next stage gives is either your signature on a fact already on record or a fact you pass as k=v. Approving re-asserts each recorded value exactly as it stands, so the signature names the commit or hash it covers, and the list shows every value before you confirm. A dry run must show the stage landing and no reached stage lost, otherwise the ticket is left for a manual tik set. A fact the ticket’s process does not declare is ignored, so one verdict can serve several processes at once.

Arguments without = narrow the batch to a process name or a ticket id prefix. Publishing a definition needs a key, given with --key or TIK_KEY.

Each fact is one signature, so with a security key a list of forty tickets is forty touches. --batch signs the tickets with one:

tik review review.verdict=approved --batch

Your key signs a single delegation on the identity registry. It names a throwaway key, the exact ticket heads in the list, and the fact paths the list sets, and it is valid for five minutes. The throwaway key is made in a private temporary directory, signs every fact, and is deleted afterwards. A ticket that changed after the list was drawn makes the batch sign nothing, because the delegation would cover an event you did not see. With several identity-registry tickets in the store, pass --registry <id>. Definitions are still signed one by one with your key. tik verify credits the facts to you as described under Store administration .

Derive facts from the world

tik probe 3184

A probe is any executable that prints key=value lines. It runs with its working directory in the ticket’s [:repo] repository, and changed values land as ordinary signed facts, so a ticket regresses on its own when reality does. The environment carries TIK_TICKET, TIK_REPO, and every present fact as TIK_FACT_<PATH>, which is what lets one repository hold many subjects — a package, tenant, or workload per ticket. A probe has ten minutes and 1 MiB of output: past the deadline it and every process it started are killed and the probe counts as failed, and longer output is refused rather than cut. Scope scripts and population commands get the same ten minutes.

Recurring and bulk work

tik recur weekly-review --period 2026-W32
tik rollout dependency-audit --parent-title "Q3 audit"

recur mints this period’s ticket exactly once: it creates only when no ticket already carries that period label. The schedule lives outside the log — run it from cron or a timer — and tik derives whether the period exists yet. rollout creates one ticket per git repository under the store, wired to a parent by link facts, so the parent is a checklist whose checkmarks derive from each child’s evidence. Re-runs create tickets only for repositories without one, so scheduling rollout keeps the checklist current as repositories appear. A scheduled run takes --period (the labels recur reads) or --at: the ticket ids and every claimed instant then follow from the process, the repository, the actor, and the period, and two replicas running the same rollout write identical events.

Standing rules

A rule that every repository of a kind must satisfy, such as “every Go module has a README”, is a process run per repository. The process’s :scope selects the population and its :probe observes the evidence:

{:process/id :readme-present
 :scope "probes/go-module.sh"     ; test -f go.mod
 :probe "probes/readme.sh"        ; prints readme=:present or readme=:absent
 :process/facts {[:readme] [:enum :present :absent]}
 :process/stages
 [{:stage/id :tracked :guards []}
  {:stage/id :holds :after [:tracked]
   :guards [[:fact= [:readme] :present]]}
  {:stage/id :retired :after [:tracked] :stage/sticky? true
   :guards [[:fact [:population :left]]]}]
 ...}

rollout asks the scope once per repository, with the working directory in that repository and TIK_REPO set: exit 0 includes it, exit 1 leaves it out, and any other exit is reported and leaves that repository out of the run with exit code 1. --scope replaces the definition’s scope for one run. Scheduling rollout --period … and probe keeps the rule current: a repository that joins the population gets its own ticket and starts short of :holds, and a compliant repository falls back from :holds when its probe observes the README gone, since :holds is not sticky. tik status <parent> counts the children per stage, and --links holds lists the compliant ones.

A repository that is deleted, or that the scope now answers 1 for, has left the population. rollout lists such tickets on every run, and with --retire it records a signed [:population :left] fact naming the reason, repository absent or outside the scope. The :retired stage above turns that fact into a sticky terminal stage, which settles the ticket: the inbox and probe sweeps leave it alone, and its history stays in the log. A repository that comes back gets a fresh ticket, and the parent’s link points at it. An unanswered scope check never retires anything. Retiring is a separate flag because a checkout that lacks some repositories looks exactly like a store whose repositories were deleted, so a scheduled run passes --retire only where the checkout is complete.

Populations without git

A rollout’s members do not have to be git repositories. Declare a population in populations.edn in the store root, beside actors, and name it with --population, or with :population in the definition:

{:products {:list ["klimpi" "cloud-portal" "Sales training"
                   {:subject "aro" :dir "aro"}]}
 :repos    {:command "aro list | cut -f1,4"}
 :staging  {:command "netbox-hosts --cluster staging"}}

A :list names its members directly, as strings or as maps of :subject and an optional :dir. A :command runs in the directory that holds the store and prints one member per line, as subject or subject<TAB>dir. A command that fails stops the rollout before anything is written, so --retire never acts on a population nobody could read.

The definition’s :subject names the fact each child carries, such as :host or [:project]; it defaults to [:project] for a population and [:repo] for the git walk. A member whose directory lies below the store’s holder also gets [:repo], so its probe runs there. A member without a directory is probed from the holder, with TIK_SUBJECT naming it. A member whose directory is missing or outside the holder is reported and left out of the run, and rollout exits 1.

{:process/id :host-patch
 :subject :host
 :population :staging
 :probe "probes/kernel-version.sh"   ; reads $TIK_SUBJECT
 ...}

tik rollout host-patch --period 2026-W47 then mints one ticket per host of the staging cluster. A member that drops out of the population is reported as no longer in population staging, and --retire records it.
