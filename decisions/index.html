Decisions

Every load-bearing choice in tik has a record: the decision, the context that forced it, and the consequences that follow. Several exist to name something tik will not do, which is the part that keeps the model small.

New here, read these four: derived state is never authoritative is the one law written as a constraint on every future feature; coordination-free is its companion; stored bytes are the hashed region is why sha256sum alone audits a store; and three clocks is why a guard’s meaning includes which clock it reads.

These files live in the repository’s knowledge bundle under kb/decisions/, so a checkout and this site carry the same record.

The laws

DecisionWhat it settles
0013Derived material may be cached only if disposable and untrusted.
0021No leader, no lock, no consensus — on any correctness path.
0001The event-log acceptance test every feature must pass.

Derivation

DecisionWhat it settles
0005Negation inside the fixpoint must be stratified to stay deterministic.
0003Concurrent conflicting assertions block guards; people resolve them.
0016Explain’s structured reasons are the stable API; the prose is not.
0018Conformance is the corpus, the laws, and the normative sweep semantics.
0019Effects observe derivation; transport is not a domain concept.
0030What a kajero notebook knows about a ticket enters it through a probe, as facts its guards read like any other.

Time

DecisionWhat it settles
0012Three clocks, never conflated; the clock is part of the guard.
0022The claimed clock is clamped to the evaluated clock.

The log and its bytes

DecisionWhat it settles
0004Parents are mandatory; the log is a Merkle DAG.
0006SHA-256, self-describing ids, one algorithm per store.
0007Stored bytes are exactly the hashed region; signatures are detached.
0008Canonical serialization is a versioned wire protocol.
0017Events are never deleted; blobs may be; nothing compacts into authority.
0020The contract every storage backend must honour.

Trust and authority

DecisionWhat it settles
0010Signatures establish authorship; authorization is derived.
0011The log admits all well-formed claims; trust is evaluated, not filtered.
0009Unknown data is handled differently per layer, on purpose.
0014The artifact hash is in the trust domain; the blob is not.
0015Definition hash is identity; publication signatures are authority.
0002Tickets pin their definition hash; migration is an event.
0023A verified key binding grants signing authority; pinned keys anchor it.
0024A link’s value names its referent; a foreign ticket carries the head observed.
0025The evidence bundle is a named, versioned format; a badge names the derivation.
0026A binding policy names which subject may bind which actor; a bound key speaks only while its token was live.
0031A pipeline run is one ticket in a throwaway store, its jobs bind their own keys, and the bundle it publishes is the only record.
0032Guards read the sticky carry from the first sweep, and :after admits a carried stage only in its own stratum.
0033A negated stage must enter for good before its negator is first judged, counting every stage reference it waits on and every negation parity.
0034A rollout takes its members from a declared population, and a subject needs no git repository.
0035A binding counts only when its token names the key it binds, through its nonce or an audience suffix.
0036Post-quantum signatures arrive as a hybrid ML-DSA-65 sidecar beside SSHSIG, with a store policy, a witness anchor, and the content hash as a parameter of the format version.
0038One shared server per organisation holds no signing keys; agents sign their own events, prove their actor per connection, and receive work through roles.
0037One signature approves a reviewed batch, through a delegation scoped to the shown heads and the verdict fact, valid for at most five minutes.
0039Proposed: the role register is a log of edits signed by authorities its genesis names by key, and a role a definition reserves for humans refuses agent actors.
0040Proposed: a local notifier pushes hints of verified stage changes to subscribers on a private Unix socket, never evidence.
0041Proposed: one backend serves several stores, each in its own context with its own key, actor, actors file, board and MCP token, and refuses to start when any store fails to open.
0042Proposed: a multi-store backend runs each pipeline as a child process on a grid with jitter, never overlapping, bounded and reported, and watches mailboxes only with DKIM at a pinned verifier and TLS that names the host.
0043Proposed: the mail bridge records a DKIM-authenticated sender of a new ticket as a keyed HMAC pseudonym, keeps the address in a private table outside the store that an erasure request empties, and refuses blocked senders before writing anything.
0044Proposed: tik.api reads, verifies and derives one ticket in process, read-only, without starting a process, with the ladder tik verify runs.
0027A pinned issuer key is identified by its kid and its key material; a reused kid keeps both keys.
0028A SPIFFE JWT-SVID binds like an OIDC token; its trust domain is its issuer.
0029A relation between tickets is its own event kind, with a closed vocabulary that no stage reads.
